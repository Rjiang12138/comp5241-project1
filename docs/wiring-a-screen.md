# Wiring a screen

Owner: R3 platform. Read this before adding behaviour to any screen under
`components/ported/`. The course editor is the reference implementation — every
pattern below is copied from working code, not proposed.

The point of this document is that four people can fill four screens without
inventing four architectures. If a screen needs something this document does not
cover, that is a platform change: raise it before writing it.

---

## 1. What "wired" means

A control is wired when all three are true:

1. It submits to a **server action** (`"use server"`, a `FormData` in, a write out).
2. The write goes through **`lib/store.ts`**, never through `prisma` from a
   component.
3. The page **revalidates** the paths whose data changed.

A control that only changes local state is not wired. It will look right in a
demo and lose its value on refresh.

## 2. The recipe

Four steps, in this order. The editor is the worked example for each.

### Step 1 — a store function

```ts
// lib/store.ts
export async function renameModule(moduleId: string, patch: { title: string }) {
  return prisma.module.update({ where: { id: moduleId }, data: patch });
}
```

Rules that have already cost us bugs:

- **Renumbering must never collide.** `Module` has `unique(courseId, position)`.
  Swapping two rows needs a three-step dance through a temporary position — see
  `moveModule`. A two-step swap throws.
- **Any sequence of position writes runs inside `prisma.$transaction`.**
  Half-renumbered modules are worse than an error.
- Ids are strings chosen by the fixture, not autogenerated, because
  `/courses/c-sef` appears in the report and in the prototype's links.

### Step 2 — a server action

```ts
// app/<area>/actions.ts
"use server";
export async function renameModuleAction(formData: FormData): Promise<void> {
  const courseId = str(formData, "courseId");
  await updateModule(str(formData, "moduleId"), { title: str(formData, "title") });
  refresh(courseId);
}
```

- **Validate in the action, not the input.** `disabled`, `required` and
  `maxLength` are courtesies. The action re-checks anything that matters —
  `resetDemoDataAction` checks the confirmation word a second time on the server.
- **Guard the role in the action.** `await requireRole("admin")` inside the
  action, not only around the page. A page guard protects the render; the action
  is a separate HTTP endpoint.
- **Revalidate every path that shows the data.** Renaming a module changes
  `/courses/[id]` *and* the module count on `/courses`. `refresh()` in
  `app/courses/actions.ts` exists for exactly this reason.

### Step 3 — a form around the existing markup

The prototype's button becomes the submit button. The markup does not change:

```tsx
<form action={removeModuleAction}>
  <input type="hidden" name="courseId" value={course.id} />
  <input type="hidden" name="moduleId" value={module.id} />
  <button className="icon-btn danger" type="submit" aria-label="Delete module">✕</button>
</form>
```

For inline editing, the input lives in its own form with the other columns as
hidden fields, and `AutoSubmitInput` submits on blur and on Enter:

```tsx
<form action={updateActivityAction} id={`act-${activity.id}`}>
  <input type="hidden" name="activityId" value={activity.id} />
  <AutoSubmitInput name="title" defaultValue={activity.title} />
</form>
```

One form per independently-saved field. Two fields in one form means saving one
of them silently rewrites the other.

### Step 4 — prove it, in this order

1. `./node_modules/.bin/tsc --noEmit` and `npm run build`.
2. `curl -F` against the action id from the rendered HTML, to prove the server
   accepts the write **without JavaScript**.
3. A real browser, to prove the control sends it. `curl` never proves this.

## 3. Where state belongs

| Kind of state | Where | Example |
| --- | --- | --- |
| Anything that must survive refresh | Postgres, via a server action | module titles, enrolment, progress |
| Ephemeral UI (open panel, typed-but-unsaved text) | `useState` in a client component | the RESET confirmation word |
| Derived values | compute during render | module count, total minutes |

If you find yourself keeping "the current course" or "the selected learner" in
React state, stop: it belongs in the URL or the database.

## 4. Screens that are not built yet

Mark them, do not fake them:

```tsx
<button className="btn" type="submit" disabled title="Lands in week 10 with the generation service">
  Generate outline
</button>
```

A control that says what it is beats a control that looks alive and does
nothing. Four screens currently fail this test — `/studio`, `/insights`,
`/path`, `/learn` — and the counts are in `docs/test-plan.md` §8.2.

## 5. Four traps, already paid for

| Symptom | Cause | Fix |
| --- | --- | --- |
| POST returns 200 but nothing is written | posted `application/x-www-form-urlencoded`; the form is `multipart/form-data` | `curl -F`, not `-d` |
| Button spins forever after a slow action | action returned state to `useActionState`; the response outlived the component | redirect with a query string, render the outcome from `searchParams` |
| Reset took 15 s and looked hung | 23 statements awaited one at a time = 23 round trips to another region | one `TRUNCATE` + one batched `$transaction` |
| A test reports "element never appeared" | `innerText` returns *rendered* text; the banner's CSS uppercases it | match case-insensitively, or assert on `textContent` |

## 6. What not to do

- Do not import `prisma` in a component or a page. `lib/store.ts` is the only
  place that knows the schema.
- Do not add a client-side fetch. Server actions are the API layer; there is no
  `/api` route for course data on purpose.
- Do not put a destructive write behind a single click. Typed confirmation plus
  a role guard, as in `components/ResetDemoForm.tsx`.
- Do not run DDL from a request handler. `npm run db:reset` drops and rebuilds
  the schema; the in-app button only clears rows.
