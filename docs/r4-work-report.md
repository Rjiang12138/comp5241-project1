## 二、已完成的具体工作

### 1. Studio 输入与材料解析

Studio 接收课程标题、教学目标、受众、目标时长和可选教学材料。材料支持 PDF，以及 UTF-8 编码的 Markdown、TXT 和 CSV 文本。CSV 在这里作为教学文本读取，不作为学生名单导入。

已增加的限制和处理包括：

- 不上传文件时，教学目标需要具有一定长度；标题和简介有长度限制。
- 一次最多选择 5 个文件；单个文件不超过 12 MiB，合计不超过 14 MiB；PDF 最多 100 页。
- 对不支持的格式、空文件、无法解码的文本和无法读取的 PDF 给出明确提示。
- 多个文件中只要有一个无法读取，停止本次生成，避免悄悄遗漏材料后仍保存课程。
- 修正文件选择状态与界面展示不一致的问题，支持清除已选文件。

### 2. PDF 图示理解

针对“PDF 中有流程图、架构图或扫描图片”的需求，增加了视觉分析流程：

1. 提取 PDF 中可选择的文字，并检查页面是否包含图形。
2. 教师可指定需要分析的页码；每次视觉分析最多处理 1 个 PDF 的 4 页。
3. 将所选整页渲染成图片，交给配置的视觉模型分析，以保留图中的位置、文字和箭头关系。
4. 将模型观察、不确定之处和页码标注为 AI 解读，传入课程生成流程，供教师核对。

图形自动识别也可能选中 Logo 或装饰图，因此允许手动指定页码。视觉模型不保证每张图都理解正确，尤其不能将图中没有写出的信息当成事实。页面图片是临时处理数据，教师仍需对照原始资料审核。

**真实测试：**使用合成的 `Client → API → Database` PDF 调用已配置的 DeepSeek 接口。模型识别了三个组件和箭头方向，也指出图中没有说明具体交互细节与返回方向。这个结果仅证明该测试样例通过，不能推广为所有图示均能准确识别。

### 3. 课程大纲质量控制

模型生成的大纲在保存前会检查：

- 模型大纲应包含 3 至 7 个不同模块；每个模块有标题、目标和 1 至 3 个支持的活动，并至少包含一个互动活动。
- 支持的生成活动包括阅读、模拟、代码练习、角色扮演和测验。
- 根据用户指定的时长重新分配活动时间，保证活动时长之和等于目标总时长，且每个活动至少 2 分钟。
- 如果包含 PDF 图示解读，课程至少需要一个阅读活动承载带来源页码的视觉观察。
- 不合格的模型结果不会直接作为合格草稿保存，而会记录原因并尝试使用内置模板；材料过短时，模板可以只生成 1 至 2 个模块，并提示补充材料。
- 如果最终检查仍然失败，提示教师修改材料或重试，不保存不合格课程。

这些检查保证的是结构和时长，**不能证明教学内容一定真实、顺序一定合理**；教师发布前仍需复核。

### 4. 测验问题修复

**判分错误：**修复部分自动生成的备用测验中，正确选项与记录的正确答案不一致的问题。针对可明确识别的历史备用题，在读取时进行兼容修正；不会因为这一兼容逻辑而直接修改数据库中的历史题目，也不会覆盖人工编辑的题目。

**答错后无法重试：**联调发现，学生选错答案后，选项被锁定、完成按钮不可用，页面却没有提供直接重试入口。已增加 `Try again`，并通过实际页面验证“答错 → 重试 → 答对 → 完成并进入下一活动”。

### 5. AI 调用记录与教师审核

Studio 现在分别记录 PDF 视觉分析和课程大纲生成的调用信息，包括用途、服务商、模型、提示词版本、调用耗时、处理结果，以及服务商实际返回的输入和输出 Token 数。没有返回的数值显示为未知，费用也不会被臆造。

其他处理包括：

- 模型结果被质量检查拒绝、改用模板，以及失败尝试会分别留下可区分的记录。
- PDF 记录包含文件名和分析页码；不把 API Key、页面图片或填充后的完整提示词写入提示词版本表。
- 模型已被调用、但未成功生成课程时，会尽可能保留与发起教师关联的尝试记录；如果记录本身保存失败，页面会提示。
- 生成草稿不等于教师审核。教师需要在发布前明确确认审核；系统记录确认人及发布版本快照。
- 如果发布时补写了此前缺失的活动内容，系统要求教师再次审核后再发布。
- 旧记录中的历史 `acceptedBy` 不能可靠证明教师已审核，因此不把它当作新的审核确认。

这部分审计针对 Studio 的视觉分析和大纲生成，不代表项目其他所有 AI 功能都已接入相同审计机制。当前演示登录是选择身份的原型流程，不等同于真实身份认证。

**数据库状态：**已准备 SQL 变更并在隔离数据库验证；尚未应用到团队共享数据库。该 SQL 不是可重复执行的幂等脚本，应由负责平台的同学结合目标数据库状态检查后协调应用。

### 6. Insights 看板改进

在联调中，系统曾根据一个模拟学生的学习记录，直接将活动类型完成率差异解释为学生流失。完成比例本身不能证明原因，因此已做以下改进：

- 在完成率旁显示已完成的“学生—活动”组合数和可能的组合总数，方便核对比例。
- 不足 5 名不同学生完成至少一个当前课程活动时，页面提示样本不足，不给活动类型排名结论。
- 5 人只是产品展示门槛，不代表统计显著；达到门槛后仍只描述数据差异，不推断因果。
- 活动类型完成率标明为累计进度；7 天、30 天筛选用于相应的尝试与提问事件，不把累计完成率误称为最近 7 天完成率。
- 每周活跃图展示最近 8 周，CSV 导出同步写出完成数、总数和时间口径。

### 7. 演示数据与演示素材

新增独立的 R4 演示数据脚本和操作说明。脚本只接受明确指定的本地数据库地址，通过事务新增专用 ID 的数据，不清空、更新或删除已有内容；如果演示课程已存在，重复运行会保持现状。

演示内容包括：

- 1 门明确标识为 DEMO 的课程，含阅读、测验和模拟共 3 个活动。
- 1 位虚拟教师、6 位虚拟学生，以及用于展示学习进度的模拟事件。
- 一张可重新生成的 `Client → API → Database` 合成 PDF。
- Insights 页面上的模拟数据提示，以及从 Studio 生成到学生学习、查看看板的演示说明。

脚本不会伪造 AI 调用、模型结果、Token 费用或教师审核记录。演示用学生行为是虚拟数据，不能当成真实用户研究结果。原有 `db:seed` / `db:reset` 会替换数据，本次演示不使用它们。

## 四、可供 R1 使用的 3 个 AI Fluency 例子

1. **明确描述与委派：**提出让 AI 识别 PDF 架构图，并要求保留图上能够观察到的信息及不确定之处。测试中模型识别了组件和箭头，也指出图中未给出具体交互细节。
2. **判断与验证：**通过实际操作测验，发现答错后无法重试；修复后重新验证答错、重试、答对和继续学习，说明不能仅因为页面能打开就认为结果正确。
3. **审慎负责：**看板曾根据单个模拟学生的数据推断流失原因。我们改为展示数据和样本量，不再从完成率差异直接断言原因，也明确模拟数据不是用户研究证据。

这 3 条是根据本次项目工作整理的候选素材，R1 在正式演讲前应结合小组实际分工和证据确认表述。

## 六、可复述的技术要点

- **为什么要保留 AI 图示的不确定性？**模型可能把看不清的细节推断成事实。把观察和不确定之处分开，并保留来源页码，教师才容易回到原图核对。
- **为什么要检查 AI 大纲？**模型可能返回不支持的活动类型、缺失互动活动或不符合目标时长的结构。保存前校验能阻止这些结构错误进入课程，但不能替代内容审核。
- **为什么记录 Token 不能直接算成费用？**服务商不一定返回实际账单，计费还依赖模型价格等信息；没有可靠依据时应显示未知。
- **为什么完成率差异不能直接解释为“课程太难”？**课程顺序、是否开始学习、样本量等都可能影响完成率；完成率展示相关现象，不能单凭它确定原因。
- **为什么演示数据必须标识？**虚拟事件适合展示页面和计算逻辑，不能用作真实学生参与率或用户反馈的证据。
